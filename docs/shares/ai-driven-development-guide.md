## 我在做什么项目？

本周在用 DVCode（DeepVCode）做三个方向的东西，目标都是让 AI 真正能融入日常开发工作流：

### 项目一：pi-go（Go 语言 Agent）

**核心理念**：市面上很多 Agent 都是 Node.js / Python 写的，动不动几百兆，跑起来资源占用不小。我尝试用 Go 做一个**完全合一的 Agent**——单二进制，零运行时依赖，系统占用极小，跑在服务器上几乎感觉不到它的存在。

但更重要的是**高度个人定制化**。市面上的编码 Agent 你只能用它给出的功能，想改点核心行为基本不可能。pi-go 的核心设计理念就是**每个组件都可替换**——Agent 循环、工具系统、压缩策略、输出格式，哪个不满意就换哪个。团队可以根据自己的业务需求灵活调整。

同时还要**节省 token**。我们通过上下文压缩、模型分级、会话分工这些策略，把 token 消耗压到最低。

### 项目二：DeepVCode 飞书集成

**解决什么问题**：开发一个功能需要盯着终端，开会或者在路上就没法用了。我们把 DVCode 接到飞书上，**无论你是在开会、通勤、还是躺床上，随时可以远程指挥 DVCode 干活**。

**产品价值**：
- 开会到一半想起来有个 bug 需要修 → 飞书发条消息，DVCode 搞定

### 项目三：EasyAgent（Python 功能集萃）

**解决什么问题**：Agent 生态发展很快，Hermes（结构化输出）、OpenCLAW（计算机控制）、Browser Use（浏览器自动化）等各个方向都有很好的开源项目。EasyAgent 就是把**社区热门的 Agent 功能集成到一起**，并且做到尽可能省token

**产品价值**：
- 追求热点的集成，无论是openclaw还是hermes，还是openhuman，这些agent靠卖点基本也就只能火一阵子，所以想着把它们一些好的功能集成进去，并且尽可能适配国产模型

## 核心理念：四会话分工

开发一个新功能时，我不会在一个对话里从头干到尾。而是拆成四个独立的 DVCode 会话，各司其职：

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  🔍 调研会话  │ →  │  📋 规划会话  │ →  │  ⚡ 执行会话  │ →  │  🔎 审核会话  │
│  DS-Flash     │    │  Sonnet      │    │  GLM-5/DVCode│    │  Sonnet      │
│  便宜模型     │    │  好模型      │    │  便宜模型     │    │  好模型      │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
     看源码              出方案             写代码              验质量
     出报告              出计划             跑测试              提意见
```

## 维护一份项目上下文

这是我认为**最关键**的一个实践：

```
docs/PROJECT_CONTEXT.md
```

这份文档是项目的高层快照——架构图、核心能力表、关键接口、文件速查表。任何新会话开始前先读它，就不用从头理解项目了。

- **维护这份文档本身用 DS-Flash 跑就够了**

### 我怎么维护的

我专门做了一个 `docs-maintainer` skill（DVCode 的自定义技能），它的工作流程：

```
扫描源码结构 → 扫描所有文档 → 差异分析 → 自动修正 → 出维护报告
```

它会检查：
- `PROJECT_CONTEXT.md` 和实际代码是否一致
- 文档索引是否完整
- 开发文档的状态流转是否合理
- 归属目录是否正确

**这个 skill 用 DS-Flash 跑就够了**，它本质上是"对比 + 整理"工作，不需要强推理。

## Handoff 机制：会话间的上下文接力

会话要结束了，但工作没干完怎么办？我用了一个 `handoff` skill（来源：[mattpocock/skills](https://github.com/mattpocock/skills/tree/main/skills/productivity/handoff)）：

```
/handoff 下一个会话要做什么
```

它会：
1. 总结当前会话的进展（做了什么、发现了什么）
2. 提炼下一步要做什么
3. 列出相关文件路径和关键信息
4. 保存到临时文件

新会话开始时，让 DVCode 读这个 handoff 文件，就能无缝接手。

**这比在脑子里记"上次做到哪了"靠谱多了。**

## 让便宜模型多试，不行再升级

这是一个很实用的省钱策略：

1. **先用 DS-Flash 试**——调研、整理、简单分析
2. **跑不通就换 GLM-5**——需要更强的代码理解能力时
3. **关键决策才上 Claude Sonnet**——架构设计、方案审核

这样做的好处：
- 大部分任务 DS-Flash 就能搞定，成本极低
- 需要升级时通过 handoff 把上下文传递给更强的模型
- 不会因为"怕做不好"而一上来就用最贵的模型

## 沉淀项目专属 Skill

Skill 是 DVCode 的自定义能力包。我会把项目中反复出现的工作流沉淀成 skill：

| Skill | 用途 | 典型模型 |
|-------|------|---------|
| `research` | 调研外部项目，产出结构化报告 | DS-Flash / GLM-5 |
| `docs-maintainer` | 维护文档结构与一致性 | DS-Flash |
| `handoff` | 会话间的上下文交接 | 当时会话的模型 |

## 文档结构管理

我维护了一套文档归属规范：

```
docs/
├── PROJECT_CONTEXT.md          # 项目上下文（最重要）
├── references/                 # 稳定查阅资料
├── decisions/                  # 采纳判断（结合调研+现状的结论）
├── research/                   # 外部项目调研原始报告
├── dev/{topic}/                # 四会话流水线的开发文档
│   ├── proposal.md             # 规划会话产出
│   ├── review.md               # 审核会话产出
│   └── execution-plan.md       # 确认后的执行计划
└── archive/                    # 已完成的开发主题
```

关键区分：
- `research/`：**我看到了什么**（外部项目的原始调研）
- `decisions/`：**我们现在准备怎么做**（结合调研的采纳判断）
- `dev/`：**具体要怎么改**（开发流水线产出）

## 成本控制总结

| 策略 | 效果 |
|------|------|
| 四会话分工 | 每个会话语境干净，token 利用率高 |
| 模型分级（三模型） | 80% 的 token 用在 GLM-5 和 DS-Flash 上 |
| 项目上下文文档 | 减少重复解释项目的 token 浪费 |
| Handoff 机制 | 避免信息丢失导致的返工 |
| 自定义 Skill | 标准化流程，减少每次的 prompt 开销 |
| 便宜模型多试 | 先用 DS-Flash，不行再升级，避免一上来就烧钱 |
| 及时归档文档 | 保持上下文文档精简，不浪费 token 读过时信息 |

## 实用建议

### ✅ 推荐做法

1. **写好 PROJECT_CONTEXT.md**——这是 ROI 最高的一件事
2. **复杂任务先规划再执行**——用 Claude Sonnet 出方案，用 GLM-5 写代码
3. **沉淀反复出现的操作为 Skill**——调研、文档维护、代码审核都是好候选
4. **会话结束前做 Handoff**——哪怕你觉得"明天还记得"，你不会记得的
5. **让便宜模型多试**——DS-Flash 搞不定再换 GLM-5，最后才上 Claude Sonnet

### ❌ 踩过的坑

1. **一个会话干所有事**——上下文爆炸，后面质量直线下降
2. **所有操作都用最贵模型**——没必要，GLM-5 写代码完全够用
3. **不维护项目文档**——每个新会话都要重新理解项目，浪费大量 token
4. **过度定制 Skill**——先用几次再沉淀，别一上来就写 skill
5. **调研报告和决策混在一起**——调研是"看到什么"，决策是"要做什么"，分开管理
